✅ Veredito: a ideia é viável — e o maior ganho vem de algo que o código já sabe fazer

O gargalo real não é a gravação na planilha: é o trânsito das fotos. Hoje as imagens viajam em base64 dentro do POST até o Apps Script e só então são reenviadas, uma a uma, para o Cloudinary — tudo dentro do mesmo pedido que o funcionário espera.

A solução de maior impacto é subir as fotos direto do navegador para o Cloudinary (o script já faz exatamente isso com o vídeo, via assinarUploadVideo_). Com isso o "salvar" passa a carregar só URLs e cai de dezenas de segundos para poucos segundos. O "salvamento em segundo plano" e a "fila" são possíveis, mas com ressalvas — o Apps Script não tem fila nativa; ela se monta com uma aba + gatilho de tempo.

01 Como funciona hoje

O cadastro de produto é uma única chamada POST para o Web App do Apps Script (action: "create"), que percorre este caminho dentro de criarProduto_:

  1. O navegador monta o corpo JSON com todos os campos e as fotos em base64 (fotoBase64, fotoStoriesBase64, fotosGaleriaBase64[]) e, às vezes, o vídeo em base64. Uma foto de 3 MB vira ~4 MB de texto; 8 fotos + capa + stories ≈ 30–40 MB de corpo.
  2. Autorização — doPostInterno_ chama permissaoDaAcao_ e autorizarAcao_, que valida o token de sessão lendo a planilha de pessoas.
  3. Roteamento — create está em ACOES_QUE_ALTERAM_PRODUTOS_, mas não em ACOES_COM_TRAVA_: então não pega o lock global de 30 s (só o contador de código pega um lock curto).
  4. Validação + anti-duplicado — criarProduto_ lê a planilha inteira (getDataRange().getValues()) para procurar nome+preço repetidos nos últimos 10 s.
  5. Upload das fotos (o ponto caro) — para cada imagem, salvarFotoCloudinary_ → cldSubir_ faz um UrlFetchApp.fetch síncrono e sequencial para o Cloudinary, decodificando o base64 no servidor. Capa + stories + até 8 da galeria = até 10 idas e voltas.
  6. Gravação — appendRow da linha, depois setNumberFormat+setValues e setValue da galeria (3 escritas), mais gravarVideo_ se houver vídeo.
  7. Histórico + push — registrarHistorico_ grava na aba Historico; se for novidade com aviso, pushEnviar_ faz uma chamada HTTP síncrona ao OneSignal.
  8. Carimbo de auditoria — despacharComCarimbo_ → carimbarProdutos_ lê 5 colunas inteiras da planilha e regrava 5 colunas inteiras (CriadoPor/Em, EditadoPor/Em, UltimaAcao).
  9. Resposta — só então o JSON volta ao navegador e o funcionário vê "salvo".

02 Onde está o gargalo

Estimativas de tempo para um produto com capa + 6 fotos de galeria, em rede móvel razoável. A ordem de grandeza é o que importa — o total hoje fica tipicamente entre 20 e 60 segundos.

🔴 Trânsito das fotos (base64) — o maior custo

O navegador precisa enviar ~30–40 MB para o Google antes de o servidor começar a trabalhar; depois o Apps Script reenvia tudo ao Cloudinary. É banda paga duas vezes e o funcionário espera as duas.

🔴 Uploads sequenciais no servidor

processarGaleriaFotos_ usa forEach com await implícito: cada foto só começa quando a anterior termina. 10 fotos × 1–3 s = 10–30 s só aqui.

🟠 Leituras da planilha inteira

getDataRange().getValues() é chamado várias vezes (anti-duplicado, carimbo). Numa planilha com milhares de linhas, cada leitura custa centenas de ms — e o carimbo lê e regrava 5 colunas completas.

🟠 Push síncrono

pushEnviar_ roda dentro do mesmo pedido. Se o OneSignal estiver lento, o cadastro inteiro espera por um aviso que não é essencial.

🟡 LockService (nas edições)

update/delete/bulkUpdate pegam o lock global com waitLock(30000). Dois funcionários salvando juntos: um espera até 30 s e pode receber "o sistema está salvando outra alteração".

🟡 Contador de código com lock

proximoCodigo_ abre um lock de 5 s e grava em Propriedades. É rápido, mas é mais um ponto de serialização em cada cadastro.

Resumo do diagnóstico: o tempo é dominado por movimentação de bytes (base64 no POST + uploads sequenciais), não pela gravação. Por isso a correção mais eficaz é tirar as fotos do caminho do Apps Script — e não "salvar mais rápido na planilha".

03 A proposta do dono, parte por parte

A ideia tem três partes. Duas são excelentes e uma precisa de ajuste de expectativa.

Parte da ideiaViável?Como ficaRessalva
Selecionar as fotos logo no início Sim Assim que a foto é escolhida, o navegador pede uma assinatura ao servidor e sobe a imagem direto para o Cloudinary, em paralelo, enquanto o funcionário preenche o resto. Precisa de uma ação nova assinarUploadFoto (hoje só existe para vídeo) e de limpeza de arquivos órfãos.
Cadastro salvo em segundo plano enquanto preenche Parcial O que faz sentido salvar em segundo plano é o rascunho do formulário (texto), não o produto. Guardar no localStorage é grátis; persistir numa aba Rascunhos a cada ~15 s é barato. Gravar o produto de verdade a cada tecla poluiria o catálogo e multiplicaria as escritas na planilha (que são caras). O produto só deve nascer no clique final.
Servidor conclui numa fila, sem o funcionário esperar Parcial Com as fotos já no Cloudinary, o trabalho restante no servidor é 1 linha + auditoria (2–3 s). Para isso, esperar não incomoda. A fila vale para o que é pesado: importação em lote, pós-processamento de vídeo, push. O Apps Script não tem fila nativa. Ela se monta com uma aba Fila + um gatilho de tempo (mínimo 1 minuto). O pedido HTTP termina quando a função retorna — não há "trabalho em background" real dentro de uma requisição.
Tradução prática: a parte "fotos no início" resolve ~80% da lentidão sozinha. A "fila" é a cereja do bolo para operações em lote — não é o que destrava o cadastro do dia a dia.

Estes são os tetos que definem o que pode e o que não pode ser feito. Valores de referência — confirme a cota da conta (Gmail comum × Google Workspace) no painel do Apps Script.

05 Desenho recomendado

Quatro fases, da maior para a menor relação ganho/esforço. A Fase 1 sozinha já resolve o problema relatado.

Fase 1 — Upload direto de fotos do navegador para o Cloudinary

Maior ganhoBaixo risco

Generalizar o que já existe para vídeo. O navegador sobe cada foto em paralelo, direto ao Cloudinary, e o "salvar" passa a enviar apenas URLs.

  • Nova ação assinarUploadFoto (ou assinarUploadMidia com tipo), reaproveitando cldCredenciais_ e a assinatura SHA-1.
  • Assinatura restrita: incluir allowed_formats=jpg,png,webp, max_file_size, folder por usuário e timestamp curto — hoje a assinatura cobre só folder+timestamp e pode ser reutilizada.
  • Cliente: FileReader → fetch paralelo ao Cloudinary → guarda a secure_url; o formulário mostra a miniatura e uma barra de progresso por foto.
  • Servidor: criarProduto_ deixa de decodificar base64 e só grava as URLs recebidas.

Fase 2 — Rascunho incremental

Ganho altoBaixo risco

Protege o trabalho do funcionário sem poluir o catálogo.

  • localStorage a cada mudança (grátis, instantâneo): se a página fechar, o formulário volta preenchido.
  • Aba Rascunhos opcional, gravada a cada ~15 s ou no botão "salvar rascunho" — leve, uma linha por rascunho, sem tocar na planilha de produtos.
  • O produto de verdade só nasce no clique final — evita duplicatas e escritas desnecessárias.

Fase 3 — Fila de processamento (aba + gatilho)

Para o pesadoMédio risco

Para operações que não cabem no pedido: importação de CSV, lote, pós-processamento de vídeo, push em massa.

  • Aba Fila com colunas JobID, Tipo, Payload, Status, Tentativas, CriadoEm, Erro.
  • Gatilho de tempo (a cada 1 min) chama processarFila_, que pega os jobs pendente, executa com lock e marca ok/erro.
  • Retry com limite (ex.: 3 tentativas) e alerta na aba Erros_Log quando estourar.
  • O doPost enfileira e responde na hora — o funcionário não espera.

Fase 4 — Processamento em lote + otimizações de planilha

ComplementarBaixo risco

O importarProdutos_ já existe (até 300 linhas, com simulação). Expor no painel e reduzir o custo das leituras.

  • Cadastro em lote: subir CSV + fotos por URL, com prévia antes de aplicar.
  • Trocar getDataRange().getValues() por leituras por coluna/índice e cachear o índice de produtos (id → linha).
  • Otimizar carimbarProdutos_: escrever só a(s) linha(s) afetada(s), não 5 colunas inteiras.
  • Push fora do pedido: enfileirar o aviso em vez de chamar o OneSignal de forma síncrona.

06 Riscos e mitigação

RiscoGravidadeMitigação
Assinatura de upload reutilizável — hoje cobre só folder+timestamp; pode ser reaproveitada para subir arquivos arbitrários. Alto Assinar também allowed_formats, max_file_size e folder por usuário; janela de timestamp curta; public_id aleatório.
Arquivos órfãos no Cloudinary — funcionário sobe fotos e abandona o formulário. Médio Job de limpeza (na fila) que apaga mídia sem produto associado após N dias, usando tags/ context e a API de administração.
Fila travada — gatilho falha e jobs ficam presos em pendente. Médio Status + contador de tentativas + alerta em Erros_Log; job com mais de X min volta para a fila.
Concorrência — duas escritas se cruzam sem lock. Médio Manter o LockService nas seções críticas; a fila processa um job por vez.
Consistência — produto aparece no site antes das fotos. Baixo Como as fotos sobem antes do clique, a URL já existe quando a linha é gravada. Validar que toda foto tem secure_url antes de salvar.
Custo Cloudinary — uploads diretos consomem banda/créditos. Baixo Comprimir no cliente antes de subir (canvas, ~1600 px, qualidade 0.8) e monitorar o plano.
Regressão no fluxo antigo — fotos já no Drive/Cloudinary e o caminho base64 legado. Baixo Manter fotoBase64/videoBase64 como caminho de compatibilidade durante a transição; migrar o painel por último.

FaseEntregaEsforçoGanho esperado

2 Rascunho incremental (localStorage + aba Rascunhos) BaixoNão perde o preenchimento; menos retrabalho

Ordem sugerida: entregar a Fase 1 primeiro e medir. Se o cadastro cair para poucos segundos, a Fase 3 (fila) deixa de ser urgente e vira melhoria para operações em lote. A Fase 2 pode ir junto com a 1, pois é barata.

// catalogo-codigo-4.8.gs — já existe para VÍDEO (linha ~498)
function assinarUploadVideo_(body) {
  const cred = cldCredenciais_();
  const timestamp = Math.floor(new Date().getTime() / 1000);
  const paramsAssinados = 'folder=' + CLOUDINARY_PASTA + '×tamp=' + timestamp;
  const assinatura = cldHex_(Utilities.computeDigest(
      Utilities.DigestAlgorithm.SHA_1, paramsAssinados + cred.apiSecret));
  return jsonResponse_({ ok: true, cloudName: cred.cloudName, apiKey: cred.apiKey,
      timestamp: timestamp, folder: CLOUDINARY_PASTA, signature: assinatura });
}

// PROPOSTA — mesma ideia para FOTO, com assinatura restrita
function assinarUploadFoto_(body) {
  const cred = cldCredenciais_();
  const timestamp = Math.floor(new Date().getTime() / 1000);
  const pasta = CLOUDINARY_PASTA + '/' + acWhats_(body.whatsapp); // pasta por usuário
  const params = 'allowed_formats=jpg,png,webp&folder=' + pasta +
      '&max_file_size=8000000×tamp=' + timestamp;
  const assinatura = cldHex_(Utilities.computeDigest(
      Utilities.DigestAlgorithm.SHA_1, params + cred.apiSecret));
  return jsonResponse_({ ok: true, cloudName: cred.cloudName, apiKey: cred.apiKey,
      timestamp: timestamp, folder: pasta, allowedFormats: 'jpg,png,webp',
      maxFileSize: 8000000, signature: assinatura });
}

}
