Resumo executivo

O frontend está funcional, bem adaptado ao uso mobile e com forte cuidado em SEO, PWA e acessibilidade. O maior gargalo atual é performance percebida no carregamento do catálogo: o LCP móvel ficou em 5,8 s, principalmente por atraso na descoberta/carregamento da imagem principal e dependência de chamadas ao Apps Script.

✅ Pontos fortes

Arquitetura estática simples, PWA completo, navegação inferior consistente, filtros úteis para catálogo, metadados ricos, sitemap/feed e camada dedicada de acessibilidade.

⚠️ Pontos de atenção

CSS e JS muito concentrados em index.html, scripts síncronos no <head>, imagens sem variações responsivas e gargalo no Apps Script.

🎯 Prioridade recomendada

Ativar uma lista pública cacheada em Worker/KV, servir imagens redimensionadas/WebP/AVIF e modularizar/minificar os assets críticos.

1. Estrutura e arquitetura frontend

Projeto majoritariamente estático, sem framework SPA pesado. A aplicação combina HTML/CSS/JS direto, Apps Script como backend operacional, Cloudflare Workers/R2 para mídia e recursos de PWA.

Leitura técnica

Boa separação por responsabilidade O projeto já separa preocupações em módulos como common.js, nav.js, pwa.js, a11y.js, pedido.js e push.js.

Dívida técnica O index.html concentra 41.964 caracteres de CSS inline e 84.684 caracteres de JS inline. Isso dificulta cache independente, minificação, testes e manutenção.

Sem framework A ausência de React/Vue reduz dependências e custo de bundle, mas exige disciplina maior em organização, testes e componentes reutilizáveis.

Recomendação estrutural: manter a abordagem estática, mas extrair o CSS do catálogo para catalogo.css e a lógica inline principal para catalogo.js, com build mínimo de minificação e versionamento por hash ou query string.

2. UI/UX e design system

A experiência é clara para e-commerce local: destaque para catálogo, busca, categorias, favoritos, sacola e contato por WhatsApp. A identidade visual preto + laranja é consistente e reconhecível.

Design tokens

Foram encontrados 9 CSS custom properties no index.html. A paleta é coesa: preto como base, laranja como ação/brand, verde para WhatsApp e neutros para textos/fundos.

Componentes UX

Há componentes úteis para conversão: chips de categoria, filtros por preço/gênero, favoritos, seleção compartilhável, sacola, CTA flutuante de WhatsApp e bottom sheets.

Feedback e estado

O código inclui toast de carregamento, aviso offline, cache de catálogo e estado de sessão/permissões — bons sinais para UX resiliente.

O que funciona bem

  • Cards de produto com imagem forte e preço legível.
  • Busca e filtros ficam visíveis logo no topo.
  • Barra inferior reduz fricção em mobile.
  • Botões têm áreas de toque adequadas e aparência clara.
  • SEO social robusto com Open Graph e JSON-LD.

Melhorias de UX recomendadas

  • Reduzir densidade visual no topo em telas pequenas: busca + filtros + chips podem competir por atenção.
  • Adicionar skeleton loading para cards enquanto a lista pública carrega.
  • Destacar visualmente “Novidades” e “Mais vendidos” se houver dados.
  • Exibir estado de “imagem carregando” ou fallback uniforme em mídia lenta.
  • Padronizar labels visíveis e nomes acessíveis dos botões de sacola.

A pontuação Lighthouse mobile foi 59. O site é leve em bytes totais reportados pelo Lighthouse, mas sofre em LCP e bloqueio de thread por dependências síncronas, imagens e chamadas ao Apps Script.

Principais gargalos

  • LCP: elemento LCP é uma imagem de card em div#grid > div.card > div.img-wrap > img.
  • Fase do LCP: 79% do tempo foi “Load Delay” (4.542 ms), sinal de descoberta/carregamento tardio da imagem.
  • API: requisições ao Apps Script levaram entre 1.455 ms e 3.965 ms.
  • Render blocking: common.js, meta.js, conta.js e Google Fonts somaram economia estimada de 790 ms se otimizados.

Imagens

P1 Lighthouse estimou economia de 1.789 KiB em imagens responsivas e 598 KiB usando formatos modernos. Priorizar WebP/AVIF, redimensionamento no Worker/R2 e srcset.

JavaScript

P2 Lighthouse apontou 18 KiB economizáveis com minificação e 29 KiB com redução de JS não usado. Extrair e minificar o JS inline ajudaria cache e parse.

Cache

P2 Dois recursos do OneSignal foram sinalizados com TTL limitado. Os assets próprios estão atrás de Cloudflare/Render; versionamento explícito facilitaria TTL agressivo.

Ação de maior impacto: o próprio código já prevê LISTA_RAPIDA_URL, mas está vazio. Publicar a lista em Cloudflare Worker/KV/R2 com cache de borda deve reduzir a dependência do Apps Script e antecipar a renderização dos cards.

Há um módulo a11y.js dedicado para labels, foco em modais, teclado e traps de foco — excelente prática.

Pontos de acessibilidade a corrigir

Lighthouse ainda registrou label-content-name-mismatch em botões .ac-sacola. O botão tem texto visível que não corresponde exatamente ao nome acessível. Ajustar aria-label para conter o texto visível ou remover divergência.

Também vale garantir alt em 100% das imagens estáticas e nos cards gerados dinamicamente.

SEO

100/100 O site possui title, meta description, canonical, Open Graph, Twitter Card, JSON-LD, sitemap e feed CSV. Muito bom para catálogo social/WhatsApp.

Segurança

Há CSP via meta tag e object-src 'none', base-uri 'self' e form-action 'self'. Melhor seria migrar CSP e headers como HSTS/Permissions-Policy para HTTP quando a hospedagem permitir.

Manutenibilidade

Não foram encontrados console. nos principais JS. Há 0 handlers inline no index.html, 11 atributos style="..." e 1 !important, bons sinais. Porém módulos antigos usam bastante var, sugerindo legado compatível, mas menos moderno.

Boas práticas observadas

  • Service worker/PWA com manifest e ícones.
  • Camada de navegação comum com cache de permissões.
  • Tratamento de sessão sem armazenar senha, conforme comentários do código.
  • CSP declarada e política de referrer.
  • Uso de try/catch defensivo para redes/recursos opcionais.

Riscos técnicos

  • Dependência crítica do Apps Script para a lista pública.
  • unsafe-inline em CSP por causa de CSS/JS inline.
  • Scripts no <head> podem atrasar renderização.
  • Falta de pipeline de build/lint/test automatizado visível.
  • Grande volume de lógica em arquivos HTML dificulta revisão e versionamento.

Plano de recomendações priorizadas

Ordem sugerida para obter ganho perceptível sem reescrever o projeto inteiro.

P1 — Alta

Cachear a lista pública fora do Apps Script

Ativar LISTA_RAPIDA_URL com Cloudflare Worker/KV/R2 e TTL curto controlado. Evidência: chamadas ao Apps Script entre 1,4 s e 4,0 s, LCP 5,8 s e 79% do LCP em load delay.

P1 — Alta

Otimizar imagens dos cards

Gerar miniaturas no tamanho real de exibição, usar WebP/AVIF quando suportado e aplicar srcset/sizes. Evidência: Lighthouse estimou 1.789 KiB em economia por imagens dimensionadas corretamente e 598 KiB por formatos modernos.

P2 — Média

Extrair, minificar e adiar scripts não críticos

Mover JS inline de catálogo para arquivo próprio, minificar common.js, pedido.js, push.js e revisar scripts síncronos do <head>. Evidência: render blocking com economia estimada de 790 ms e 18 KiB economizáveis por minificação.

P2 — Média

Separar CSS crítico e CSS completo

Manter apenas CSS acima da dobra inline ou carregado prioritariamente, movendo o restante para arquivo cacheável. Evidência: 41.964 caracteres de CSS inline no index.html.

P2 — Média

Corrigir nome acessível dos botões de sacola

Sincronizar texto visível com aria-label em .ac-sacola. Evidência: Lighthouse sinalizou label-content-name-mismatch.

P3 — Baixa

Modernizar gradualmente módulos legados

Converter var para const/let onde seguro, adicionar lint/format e testes simples de funções críticas. Manter compatibilidade se houver requisito de browsers antigos.
